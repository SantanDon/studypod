# StudyPod release gates

The release decision belongs to observed user journeys on the built app and the exact deployed candidate. Passing unit tests or receiving a successful generation response is insufficient evidence of working audio.

## Before deployment

Use Node 22 and the repository's existing open-source configuration. No cloud credentials, account signup, Ollama model, or paid provider is needed for this deterministic gate:

```sh
npm ci
npx playwright install chromium
npm run typecheck
npm run lint
npm test -- --run
npx vitest run --config vitest.config.ts src/__tests__/integration/podcastChatCommands.test.tsx
npm run build
npm run check:bundle
npm run test:e2e
```

`test:e2e` starts the production build's Vite preview on `127.0.0.1:4179` with a strict port. Build first; it does not rebuild automatically. It refuses an externally configured `STUDYPOD_BASE_URL`. Each test starts with a fresh browser context and guest storage. Desktop (1440px) and touch mobile (390px) exercise dashboard entry, keyboard menu dismissal/focus restoration, the GitHub link, missing-route recovery, local notebook creation and reload persistence, Sources/Chat/Studio navigation, horizontal overflow, and unavailable audiobook recovery.

These are real built frontend assets and real browser IndexedDB operations. Guest profile lookup is a fixture returning no signed-in user; it does not validate real authentication. Vercel analytics is an empty local script fixture. The audiobook `/voices` response is explicitly a fixture with all generation capabilities disabled. External resources are intercepted; HTTP mutations are rejected. This suite proves the UI does not offer upload/generation when the runtime is unavailable. It proves neither real provider audio nor successful ingestion, authenticated sync, source-grounded answers, podcast generation, decoding, playback, or export. Google fonts and external analytics are not part of this deterministic gate.

Screenshots, failures, traces, browser observations, JSON results, and HTML reports go to `.ai-bridge/studypod-browser-gate/` (ignored by Git). Override with `STUDYPOD_BROWSER_ARTIFACTS`. CI runs this gate after its production build and retains evidence for 14 days. Browser test files use `.pw.ts` so Vitest does not collect them.

## Required real audio acceptance

Before promoting any audio mode as working, run it with a real configured provider on the candidate runtime using a small authorized source with known facts. Record the exact candidate SHA, runtime URL, provider/model/voice, source checksum, device/browser, timing, failures, and exported-file checksum. Keep secrets out of receipts.

1. Select a source and verify the selected material reaches generation. For read-aloud, check opening, middle, ending, ordering, omissions, and unexpected invented material. For podcasts, check factual accuracy, citations/source relationship, speaker count, and chosen solo/discussion mode.
2. Observe progress and cancellation. Force a provider/network failure; verify an actionable error, retry without duplicate jobs, and no premature completion claim.
3. Play real audio on desktop and mobile: audible speech, advancing duration/time, pause/resume, seek, speed, ending, and recovery after navigation/reload. Confirm microphone/device interactions if the flow supports them.
4. Export the actual file, open it independently, check duration/format, and listen to its beginning, middle, and ending. A non-empty Blob or HTTP 200 alone does not pass.
5. A human listens for intelligibility, clipping, truncation, awkward pacing, voice/speaker consistency, and source fidelity. Include any local Qwen critique as advisory evidence, clearly separated from browser receipts and human listening.

Run this for each advertised mode/provider, including a supported local configuration when claiming local compatibility. Mock providers can test controls and error recovery; they can never satisfy real audio acceptance. A local full-book pass does not establish Vercel full-book support. A deployment with disabled audiobook capabilities must show that limitation honestly and must not advertise cloud read-aloud as available.

## After deployment: read-only smoke

Run only against the exact candidate URL. Example PowerShell:

```powershell
$env:STUDYPOD_BASE_URL = 'https://your-exact-candidate.vercel.app'
$env:STUDYPOD_EXPECT_AUDIOBOOK_ENABLED = 'false'
$env:STUDYPOD_BROWSER_ARTIFACTS = '.ai-bridge/studypod-postdeploy-candidate'
npm run test:production-smoke
Remove-Item Env:STUDYPOD_BASE_URL, Env:STUDYPOD_EXPECT_AUDIOBOOK_ENABLED, Env:STUDYPOD_BROWSER_ARTIFACTS
```

The smoke uses fresh guest contexts, verifies desktop/mobile dashboard, keyboard/profile and layout, and performs real GET requests to `/api/health` and `/api/audiobook/voices`. The capability request uses the fresh browser's validated guest ID as its Bearer identity, matching the frontend contract; the identity is not printed in receipts. It creates no accounts/notebooks, uploads nothing, and sends no generation requests. The expected enabled flag defaults to false; set it true only when enabled full generation is an explicit, verified deployment claim. The browser blocks HTTP mutations and external resources. GET endpoint failures or capability mismatches fail the smoke. This is a deployment entry/capability check, not a production audio listening test.

The signed-out cookie bootstrap is a narrow recorded exception: real same-origin GET `/api/user/profile` status 401 is expected without a signed-in session. After that observation, one POST each to `/api/auth/refresh` and `/api/auth/signout` is blocked and recorded as expected bootstrap behavior. The app implements this recovery in `ApiService.getUser` and `AuthContext`; these blocked requests do not prove a backend defect or validate real session refresh/signout. Their correlated Chromium resource errors are classified only for the exact same-origin resource URL, exact error text, and bounded event count. Empty resource locations, other 401s, repeated POSTs, unexpected mutations, and unrelated console/HTTP errors remain failures. See the `expectedGuestBootstrap` attachment alongside `errors`; nothing is silently discarded.

Record deployment URL, deployed SHA/build identity, command, time, artifacts and decision together. If predeployment journeys fail, stop release and fix/retest the affected path. If postdeployment entry/capabilities fail, stop promotion and choose a repair or rollback through the human-controlled deployment workflow. If audio acceptance is missing, describe only the modes actually verified. Neither this document nor a test pass authorizes publishing, deploying, rollback, or production data changes.


## Real authenticated account/data gate

Run `npm run test:auth:local` after installing frontend/backend dependencies and Chromium (`npx playwright install chromium`). The runner builds the current checkout, starts a disposable file database/backend on 127.0.0.1:4018 and built preview on 127.0.0.1:4178, generates two synthetic `.invalid` test identities, and runs desktop plus 390px touch/mobile browser contexts. Ports must be free. It does not use the live database. Existing environment keys are blanked, JWT is process-only random, TOKENLLM7 and OVHCLOUD are disabled and OLLAMA_BASE_URL is empty. Local signup uses the disposable sandbox identities; no mailbox or cloud account is created.

`e2e/authenticated.auth.ts` drives real signup/login and cookie sessions, creates a notebook and a small synthetic pasted source, signs out, rejects a wrong password without leaving the login screen, then logs in with a fresh browser context and verifies the source from the real server and UI. Profile responses must identify the expected account after signup/login, fresh login and second-account login. A signed-out source request must be denied; a second dedicated account must not list or read the first account's notebook or sources. Successful owner PUT controls establish that notebook/source write routes work before cross-account PUT requests must be denied, with the original owner title/content verified unchanged. No auth/notebook/source responses are mocked. Same-origin `/api/ai/generate` is aborted; this guard is not a comprehensive provider/network isolation check. Provider acceptance remains a separate gate.

CI runs the isolated gate and uploads only desktop/mobile `report.json`. The custom reporter emits scenario status, last phase and explicitly sanitized acceptance fields; the public report never includes error objects, locator logs, environment, DOM, credentials, cookies or tokens. Credential-redacted failure diagnostics are written separately to ignored diagnostics.private.json and must not be uploaded. Traces/video/screenshots are off. All local credentials, databases and raw server/build logs remain in ignored `.ai-bridge/.../release-gate/auth-local/<run>/`; do not upload that parent directory. Failure receipts identify the pending phase; private logs remain available for bounded local diagnosis. `PLAYWRIGHT_NO_COPY_PROMPT=1` prevents the automatic failure context snapshot in the runner.

For an authorized cloud run, copy `e2e/auth.env.example` to ignored `.env.auth.local`, explicitly set the HTTPS target, two dedicated account credentials, and `STUDYPOD_AUTH_MUTATIONS_ALLOWED=dedicated-test-data`, then run `npm run test:auth`. Existing accounts use STUDYPOD_AUTH_SIGNUP=0. Creating dedicated cloud accounts additionally requires an explicitly authorized identity and terms acceptance (STUDYPOD_AUTH_SIGNUP=1 and STUDYPOD_AUTH_TERMS_ACCEPTED=1). Never substitute a personal production account. This creates only synthetic QA notebooks/sources and performs no destructive cleanup. Run desktop and mobile separately with STUDYPOD_AUTH_MOBILE=0/1 and separate artifact directories. No cloud mutation run has been performed while identity/terms remain unresolved.

This is an authenticated account/data slice, not full release readiness. File uploads, grounded chat, provider generation, audio playback/export/listening, recovery, MFA, billing and broader ownership/security behavior need separate real acceptance scenarios. Local success cannot prove deployed cloud auth/data behavior; repeat this authorized cloud slice against the exact deployment and retain postdeployment read-only smoke evidence before promotion.

## Full source-to-Studio acceptance

Run `npm run test:flow:local` (the runner is `e2e/run-full-flow-local.mjs`). It builds an isolated candidate, uses a disposable database and dedicated synthetic accounts, and keeps existing development ports and data separate. It requires local Ollama with the configured Qwen model; audio acceptance also requires the configured real speech provider. Run one inference suite at a time. Do not substitute mocked generation for this gate. The executable test configuration and each run's report determine which scenarios actually ran; the presence of a test file is not a pass.

For each advertised intake type, require a successful browser upload/import, readable extracted content with known facts, owner persistence after sign-out and fresh login, grounded chat with an inspectable citation that survives reload, and a generated Studio artifact with checked content. Cover TXT, Markdown, PDF, DOCX, EPUB, WAV, MP3, M4A, pasted text, website, YouTube and bookmark import. Extraction success alone does not establish downstream success. Public website/video fixtures need their actual current content; unavailable upstream content must produce a recorded failure or explicit unsupported state.

Upload recovery is part of this gate: in a fresh guest notebook, upload four valid sources and one corrupt supported document using the native file chooser. The corrupt source must show a retained actionable failure reason after the toast disappears and after reload. At the five-source limit, delete that failed source through the UI, then upload a valid replacement and verify its readable facts after reload. Repeat a failed upload with a dedicated signed-in account. A queued record, HTTP success, or restored quota in a unit test alone does not pass this browser recovery journey. A failed save of extracted text must be distinguished from an extraction failure. Test both a rejected content save with an acknowledged failure marker and a rejected content save whose failure marker also cannot be saved. Dismiss the toast and reload: the source must retain an actionable interruption, preserve other sources, and support confirmed removal and native re-upload. Any browser recovery receipt must contain only source identity, filename, stage, timestamp and a fixed reason, scoped to the owning account and notebook; it must not contain document text or file bytes. Keep these deliberately injected failures separate from normal real-provider acceptance. An API outage that leaves a source pending or uploading without a usable recovery is a recorded failure.

Native upload validation must cover a mixed batch containing valid files, a corrupt supported document, an empty file and an actual file above the advertised size limit. Check rejected filenames and reasons, verify rejected files create no source records, and verify valid files proceed independently. After reload, retained valid content and corrupt-file recovery must still work, and selecting another valid file must succeed. Keep native picker, keyboard activation, cancellation and drag/drop evidence distinct from tests that inject File objects. Reload during a queued upload must leave an actionable recovery path for affected source records; transient in-page queues cannot prove recovery. While the original page still owns a healthy upload, a recovery record must not falsely label it interrupted.

For guest recovery, require an acknowledged local storage write before reporting a completed source or successful removal. If storage and its cleanup retry both fail, preserve the persisted source, recovery receipt and quota. A success toast or quota change without a saved mutation is a failure. Guest receipts must use the guest identity and verified owning notebook; authenticated receipts must retain their separate account scope.

Studio acceptance must exercise flashcards through every card and saved review progress, quizzes through feedback, saved results, history reopening and retry, notes with preserved titles/content, mind maps, source comparison, missions and their saved notes, research goals and synthesis, suggested-goal acceptance, document revision approval, version restore and all advertised export formats, and chat actions that open audio tools. For authenticated decks and quizzes, verify server persistence in a fresh browser context and reject access from a second account. Do not accept legacy browser storage as evidence of authenticated ownership.

Run the applicable journeys on desktop and touch mobile. Save the candidate identity, fixture hashes, provider/model, stage outcomes, page errors and sanitized receipts. A partial or failed matrix keeps release readiness false even when focused code tests pass. Repeat the authorized authenticated journeys against the exact cloud candidate before and after release; the read-only smoke above covers only entry and capabilities. Cloud signup remains gated on the dedicated test identity and terms acceptance.

The current `StudyPod Quality` workflow runs the deterministic browser gate and isolated authentication slice. It does not run this complete source/provider/Studio gate or verify the deployed candidate. A green workflow therefore cannot authorize release or promotion by itself. Retain a separate completed full-flow report for the exact candidate and the authorized cloud results. Keep upload fault-injection receipts separate from normal source/provider results: a deliberately failed source-save request proves recovery behavior only, while the normal journeys must use the real backend and providers without that interception.

The full-flow reporter's `report.json`, attached receipts, process logs and database are **local private diagnostics**. Attachment names containing “sanitized” do not establish that arbitrary provider errors or source text are safe to publish. Do not upload the run directory or detailed report to CI artifacts. `decision.json` contains only constrained scenario identifiers, statuses, counts and fixed coverage boundaries; it is the shareable status artifact. A grep/project selection is explicitly a diagnostic subset and cannot pass its complete local execution flag. `e2e/acceptance-contracts.mjs` defines an independently reviewed inventory of 55 desktop and 42 mobile scenarios, separate from test discovery. Both discovery and observed results must match that exact inventory. Schema-v2 receipts must match their scenario and project, record the required terminal state and stages, and satisfy feature-specific evidence rules. Audio receipts additionally require real media state, exported-file signal/hash, source/script/transcription checks, fresh-owner restoration and foreign-account denial. Removing a format, omitting mobile coverage, duplicating or substituting a scenario, or lowering the reported expected count cannot pass the complete gate. This inventory covers the implemented journeys; it does not claim every possible device or product behavior is tested. The final runner decision also binds execution to the recorded HEAD and source, built asset and fixture hashes, with all stability checks passing and a successful test process. Missing or malformed receipts, skipped cases, subsets and candidate drift fail closed. Cloud before/after acceptance remains `not-run` and `releaseReady` remains false until those independent gates exist and pass.

The local runner records `candidate.json` with HEAD and hashes of relevant source files, built assets and generated fixtures. It compares source state before and after building, then compares source, assets and fixtures again after execution. A changed candidate fails the runner. Detailed file inventories remain private. A complete execution decision must be paired with this stable candidate record; HEAD alone does not identify a dirty working tree. The runner disables browser-direct Ollama discovery and exercises authenticated server generation using local Qwen. Normal builds keep that discovery disabled unless `VITE_ENABLE_OLLAMA=1` or `true` is set.
